1. What “harness” even means — verified definition

Two 2026 sources now converge. Birgitta Böckeler (Thoughtworks) on Martin Fowler's site defines the outer harness for coding-agent users as everything around the model that shapes what it does — split into Guides (feedforward) and Sensors (feedback), each either computational (CPU, deterministic) or inferential (LLM, probabilistic) [martinfowler.com — Harness engineering for coding agent users, 2 Apr 2026]. The harness is a cybernetic governor — a steering loop the human improves whenever the same failure repeats.

Lilian Weng frames it for self-improvement: Agent = Model + Harness where the harness is the system surrounding the base model that decides how it thinks, calls tools, manages context, stores artifacts, and evaluates. The near-term path to recursive self-improvement is not the model rewriting its weights, but the harness becoming an optimization target [lilianweng.github.io — Harness Engineering for Self-Improvement, 4 Jul 2026].

One sentence: The harness is the platform layer of the coding agent — tools, prompts, skills, hooks, memory, and feedback loops. The model is the reasoning; the harness decides what it can see and what happens after it acts. See also Harness Engineering Guide (open-source, bilingual EN/中文) and harness-engineering-practice (EN/中文/한국어/日本語).

Regulation categories (Böckeler) — the harness regulates three dimensions, by increasing difficulty: maintainability (easiest today, linters exist), architecture fitness (fitness functions), and behaviour (the elephant — functional correctness). Our bare-bones sits in maintainability + behaviour via `pytest` [martinfowler.com].

2. Why harness > model now

Weng's second point is blunt: with modern models, harness engineering will evolve toward meta-methodology — improving the machinery for getting answers, not just the answer. Once harness design is code, a strong coding agent can search that design space [lilianweng.github.io].

Evidence: tool format matters more than size

Hashline 6.7% → 68.3%

Same cheap model (Grok Code Fast 1), same prompt — changing only the edit format (Hashline line-anchored patches in can1357/oh-my-pi) ten-xed success on code-edit tasks [blog.can.ac — The Harness Problem, 12 Feb 2026; summarized on yuv.ai]. Harness > model.

Evidence: harness shifts completion

AHE: observability-driven evolution

Holding the base model fixed, harness edits materially shift long-horizon completion. AHE's three observability pillars (component / trajectory / decision) turn each edit into a falsifiable file-level contract [arxiv.org — Agentic Harness Engineering, Lin et al., Apr 2026].

OpenAI's Codex retrospective makes the same claim: the breakthrough was not the model but the harness — sandboxed tools, verification loops [Harness Engineering — What Is Harness (citing OpenAI)]. Ryan Lopopolo (LangChain) puts it as All the harness should do is surface instructions at the right time [gist — Harness Engineering summary (AI Engineer talk)].

3. What we built (bare-bones, on purpose)

We chose minimal earendil-works/pi (4 tools: Read/Write/Edit/Bash) over the feature-rich fork can1357/oh-my-pi (31 tools, LSP+DAP, Rust core) precisely because bare-bones teaches. OMP is the comparison in Week 5, not the base.

Repo v1.0 frozen dev 5/5

AGENTS.md:1 + skills/python-conventions/SKILL.md + skills/review-sensor/SKILL.md (guides)
extensions/index.ts:1 (session_start playbook, tool_execution_end ruff, session_shutdown trajectory)
sensors/computational.ts:1 (ruff via uv fallback) + sensors/judge.ts:1 (qwen2.5-coder:7b)

src/app.py:1 (health/echo/items) + tests/test_*.py

Bare-bones on purpose

No vector DB, no Harbor, no dashboard yet. File-memory + deterministic verifier + one inferential judge — enough to demonstrate the steering loop and to interview-explain every file line. PLAN.md is private; playbook.example.md is the public template.

Why bare-bones is a feature: Böckeler warns legacy codebases are hardest to harness where harness is most needed (harnessability) [martinfowler.com]. A minimal repo lets us bake harnessability in from day one — strongly typed, clear module boundaries — and then add harness templates later.

4. Guides (feedforward) — increase P(success first try)

Guides anticipate unwanted outputs. In our repo they are inferential (the model must interpret) and versioned:

  • AGENTS.md:1 — project conventions (write plans to memory/short.json, every Write → sensors/computational.ts, every run → runs/<id>/trajectory.jsonl)
  • skills/python-conventions/SKILL.md:1 — FastAPI + Pydantic v2, src/ layout, tests/test_*.py
  • skills/review-sensor/SKILL.md:1 — now documents both sensors and auto-run (see next section)
  • memory/playbook.md:1 — ACE-style bullets id: description | source | date (e.g. py-004: Use Pydantic BaseModel for POST JSON body — pi failed sample-02 with Field required | sample-02:q2c8)
Verified pattern: Böckeler's feedforward examples include AGENTS.md, Skills, bootstrap scripts, and LSP context as computational guides [martinfowler.com]. The AIware '26 study (Harness Engineering for Agentic AI Coding Tools) found 17.3% of repos now use tool-agnostic AGENTS.md and that harness engineering today is mostly context engineering — static files over executable hooks [arxiv 2602.14690].

Computational guide we use: LSP is not yet wired, but uv run --with ruff is the fast deterministic guide the extension invokes after each Write. It is cheap enough to run every loop [martinfowler.com].

5. Sensors (feedback) — computational vs inferential

Sensors observe after the agent acts and let it self-correct before human review. The cheapest signal that actually optimizes for LLM consumption wins (Böckeler: custom linter messages that include instructions for self-correction — a positive kind of prompt injection).

Computational — CPU, cheap, every Write

sensors/computational.ts:1 → ruff

Deterministic, 50ms–1s. Tries ruff check then uv run --with ruff fallback (fixes broken py launcher on Windows). Injected as <sensor type="computational">Fix this before continuing</sensor>. Catches I001/F401/F821 reliably.

Böckeler: computational sensors catch structural stuff reliably — style, boundaries, coverage [martinfowler.com].

Inferential — LLM, expensive, after task

sensors/judge.ts:1 → qwen2.5-coder:7b

Semantic, ~10s, via Ollama http://localhost:11434/v1. Prompt checks duplicate/over-engineer/missing tests. Falls back to heuristic (dup-line + length) if Ollama down. Output is PASS/FAIL + fix hint sized for LLM.

Böckeler: inferential sensors increase trust with strong models but are probabilistic [martinfowler.com]; Weng: they are slower/more non-deterministic, keep them outside the inner loop.

Where they run (keep quality left): computational after every Write via extensions/index.ts:24 (tool_execution_end), inferential after task via npm run judge -- <file|runs/<id>> and auto via sensors/run-eval.ts:1 on any FAIL (see Thoughtworks Sensors deep-dive (May 2026) for the TypeScript dashboard experiment with ESLint/Semgrep/DepCruiser/mutation testing).

Auto-run as skill: skills/review-sensor/SKILL.md:1 now documents both sensors and that run-eval.ts auto-calls judge.ts on FAIL — no reward hacking, verifier stays outside the generation loop [Weng].

6. Memory as files — ACE, sleep, self-improve

Weng's second recurring pattern: file system as persistent memory. Don't shove trajectories into context; keep durable state in files. LLMs already know bash/read/edit, so file-memory benefits from core capability gains [lilianweng.github.io].

Our implementation: runs/<id>/trajectory.jsonl:1 (episodic, one JSON per run, includes playbook snippet) + memory/playbook.md:1 (semantic, ACE bullets) + memory/short.json:1 (working memory). Files are gitignored; playbook.example.md is the public template. The evaluator and permission control live outside the loop that evolves the harness (Weng's Future Challenge 5).

ACE → MCE → Meta-Harness lineage

ACE (Zhang et al., ICLR 2026) treats context as an evolving playbook with Generator/Reflector/Curator that merges itemized bullets deterministically, not blob rewrites [Weng § Context Engineering]. That's exactly memory/sleep.ts:1.

MCE (Ye et al., 2026) separates mechanism (F_s dynamic operators) from artifact content (ρ_s static prompts) and evolves free-form skills via bi-level optimization [Weng].

Meta-Harness (Lee et al., 2026) optimizes the code that decides what to store/retrieve/present — a harness for harnesses, kept on the Pareto frontier [Weng].

Self-improving harness on our repo

memory/self-improve.ts:1 implements the propose-evaluate-accept loop from Self-Harness (Zhang et al., 2026): weakness mining (trajectory notes + eval reports), bounded proposal (one bullet), validation on held-in (sample-01,02) + held-out (sample-03) via sensors/run-eval.ts:1, revert on regression. First run proposed py-006: response_model/status_code → validated 3/3 → kept, second run → no new weakness — idempotent. This mirrors the paper's constraint that qualified edits must have no regression on both splits.

Weng's caution: STOP improved with GPT-4 but degraded with GPT-3.5 — base model must be capable enough to improve the mechanism; harness-benefit is non-monotonic, middle-tier models benefit most [lilianweng.github.io — citing Zelikman et al. STOP & Lin et al.]. We see this with llama3.1:8b (printed JSON, no tool call) vs qwen2.5-coder:7b (10s judge PASS) vs openrouter/gpt-4o-mini ($0.00022 toolUse success).

7. Eval harness — verifier outside the loop

Behaviour harness is the elephant: how do we know the app functionally behaves? Böckeler's current best practice is a spec + AI-generated tests with human review — not enough trust alone [martinfowler.com]. Our answer is minimal and Windows-friendly: tasks/*.yaml with a deterministic verifier per task.

sensors/run-eval.ts:1 parses YAML (custom, no dep), normalizes python → uv run and pytest → python -m pytest (so src/ is found), runs via powershell.exe -Command / bash -c, auto-calls judge.ts on FAIL, and writes runs/eval-<id>/report.md + report.json with Score: 5/5. Early run with curl | grep failed on Windows (no grep, no live server); we switched to TestClient — a portability lesson.

Weng's Future Challenge 1 is exactly this: weak/fuzzy evaluators for research taste vs measurable verifiers. For code, fast precise verifiers exist; for taste, not yet [lilianweng.github.io].

8. Live loops: 3 failures we actually hit (and what they taught)

1. Sample-02: POST body as query param Field required

pi --provider openrouter/gpt-4o-mini wrote async def echo(message: str) → pytest FAIL Field required @ query.message. Computational sensor had already flagged I001/F401 x4. Fix: Pydantic class EchoIn(BaseModel): message: str + def echo(body: EchoIn) → 4 passed. New bullet py-004.

2. Sample-03: mangled Item model F821

Pi overwrote src/app.py with class Item: message: str stray and lost EchoIn → F821 Undefined name EchoIn + pytest NameError (0 collected). Fix: restore + ruff --fix → 3 passed. New bullet py-005: preserve existing models.

3. Ollama tool calling 24% → 100% pull, still no toolUse

Local llama3.1:8b and qwen2.5-coder:7b via ollama http://localhost:11434/v1 + openai-completions printed {"name":"write"...} as text, not toolUse — no file created. openrouter/gpt-4o-mini with same prompt did toolUse correctly ($0.00022). Lesson: harness-benefit depends on model; local judge still works (qwen 12.6s PASS) even when local actor doesn't.

Each failure was logged to runs/<id>/trajectory.jsonl, then promoted to a playbook bullet via sleep/self-improve — the steering loop Böckeler describes: whenever an issue happens multiple times, improve the harness so it becomes less probable.

9. Why minimal pi for learning (vs OMP)

earendil-works/pi is the monorepo at github.com/earendil-works/pi (also pi.dev): @earendil-works/pi-ai (unified LLM), @earendil-works/pi-agent-core (loop), @earendil-works/pi-coding-agent (CLI/TUI). It ships 4 tools and intentionally skips sub-agents/plan/todos — write plans to files, use tmux [README]. Extensions add capabilities via export default function(pi: ExtensionAPI) { pi.on("session_start", ...); pi.on("tool_execution_end", ...) } [extensions.md, providers.md (Ollama baseUrl http://localhost:11434/v1 + compat.supportsDeveloperRole), models.md].

can1357/oh-my-pi (OMP) is the batteries-included fork (31 tools, 14 LSP ops, 28 DAP ops, ~80k Rust, Hashline) — the right comparison for Week 5, not the base. Choosing minimal pi let us own every guide/sensor/memory decision and explain it line-by-line — exactly what makes harnessability intentional for greenfield vs hard for legacy [martinfowler.com — Harnessability & Ambient affordances].

10. What's next — meta-harness for v1.1

v1.0 is frozen 4/4 (now 5/5 on dev). v1.1 is the step from toy tasks to production evals: pi-metaharness (@oh-my-pi/pi-metaharness in can1357/oh-my-pi/packages/metaharness) — one manager for Harbor, TypeScript-edit, and SnapCompact with experiment → run → trace, SQLite metaharness.sqlite, REST :4700 + SSE, and trace-report.ts narratives [metaharness README].

  • Start with edit benchmark (TypeScript mutations, cheap, local) to quantify Hashline — no Docker/KVM needed.
  • Then Harbor terminal-bench@2.0 subset (20 tasks) via Docker on WSL — our machine has WSL+Docker; public registries only, models.yml via host gateway so keys never enter containers [metaharness README — How Harbor runs execute].

Design stays the same: proposer is itself a coding agent, harness candidates live on the Pareto frontier, history stays file-system (grep/cat), permission control lives outside the loop that evolves the harness [Weng — Meta-Harness outer loop]. We'll keep the evaluator verifier-independent and trace-audited — the same anti-reward-hacking discipline as run-eval.ts.

Open questions we carry: When sensors never fire, is that high quality or inadequate detection? How far can we trust agents when guides and sensors contradict? How to keep the harness coherent as it grows? [martinfowler.com — A starting point] + Weng's 7 Future Challenges: fuzzy evaluators, memory lifecycle, negative results, diversity collapse, reward hacking, long-term repo health, human oversight [lilianweng.github.io].
